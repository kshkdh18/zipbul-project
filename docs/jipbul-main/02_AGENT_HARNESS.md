# 짚불 에이전트 하네스 설계

버전: 1.2 · 상태: **개발 승인 완료, 핵심 시연 이후 단계적으로 확장**

[전체 제품·기술 기획](./01_MVP_DEFINITION.md)의 분석 실행부를 구체화한다. 아래 역할·프롬프트 구성·도구 계약은 설계이며 실제 에이전트 실행이나 구현용 원샷 프롬프트가 아니다.

## 1. 하네스가 담당하는 일

하네스는 모델의 작업 문맥·도구·상태·검증·재시도·저장을 관리하는 코드다. Astra가 필요한 추가 관찰을 선택할 수 있게 하되, 실제 실행과 결과 공개는 타입이 있는 도구와 검증 절차를 거친다.

**Node worker의 상태 머신이 실행을 관리하고, Astra 역할들이 관찰·연결·관계·검증을 수행한다.** 별도 범용 에이전트 프레임워크나 무제한 자율 루프를 필수 의존성으로 추가하지 않는다. OpenAI SDK와 앱의 계약·상태 머신으로 시작한다.

이 문서의 에이전트는 제품 내부의 논리적 역할이다. 역할마다 별도 서버를 만들거나 매 요청마다 모든 역할을 호출하지 않는다. 1차 모델 기반 처리는 모두 `gpt-6-astra`다. Decisions 연동은 Astra 기준선의 실제 평가에서 수요가 확인된 뒤 검토하며, 1차 호출 경로에는 포함하지 않는다.

**단계 1:** 두 모드·게임 장면·이동·수동 연결·영상 근거·기본 그래프를 먼저 완성한다. 실행부는 Astra 호출, ID/근거 검증, 상태·결과 저장, 실패·취소·사람 검토 보존부터 구현한다. **단계 2:** 핵심 시연 통과 후 아래의 역할별 도구 루프·다단계 검토·복구를 확장한다. 전체 하네스 완성을 화면 구현의 선행 조건으로 삼지 않는다.

단계 1부터 사용자 매핑을 분석 결과와 별도로 보존한다. 분석은 원본 GLB 중심, 워크스루는 사실적 품질을 우선한 보완 장면 중심으로 표시한다. 보완 자산은 원본 entity ID와 근거를 유지하며 모델이 실측 객체나 원본 증거로 승격하지 않는다. 보정 구간의 시뮬레이션 안내선은 모델 판단이 아니라 현재 장면의 충돌·접지 검증 결과로 허용한다.

## 2. 역할과 책임

| 역할 | 입력 | 출력 | 제한 |
| --- | --- | --- | --- |
| 관찰·위험 분석 | 시간·ID가 붙은 원본 프레임, 대상 정의 | 관찰·위험 후보·근거 영역·추가 관찰 요청 | 이미지에 없는 사실이나 임의 XYZ 생성 금지 |
| 공간 연결 보조 | 후보·GLB 객체/표면 목록·알려진 장면 뷰 | entity/anchor 대응 후보와 이유 | 후보 ID 밖의 대상 생성, 자동 검토 확정 금지 |
| 관계 구성 | 검증된 객체·근거·위험·공간 목록 | 의미 있는 관계, 점검 순서, 미확인 연결 | 인과관계와 이동 가능성 단정 금지 |
| 근거 검토 | 원본 프레임과 위 역할의 결과 | 근거 일치·반례·누락·수정 요청 | 단순히 다른 역할의 설명만 보고 통과시키지 않음 |
| 대화·표현 | 현재 결과 revision, 선택 ID, 질문 | 근거 있는 답변과 허용된 표현 지시 | 검토 상태 변경·실제 안전 확정·임의 코드 실행 금지 |

기본 실행에서 관찰 역할은 프레임 묶음별로, 관계 역할은 통합 단계에서, 근거 검토는 결과 공개 전 필요한 묶음에 대해 실행한다. 공간 정보가 부족하면 공간 연결 보조를 생략하고 수동 대응으로 연결한다. 대화·표현 역할은 사용자 상호작용 시 실행한다.

같은 Astra를 여러 역할로 사용해도 판단이 독립적이거나 정답이 보장된다고 주장하지 않는다. 근거 검토는 원본과의 대조를 추가하는 장치다.

## 3. 실행 구조

```text
사용자: GLB + 원본 영상 접수
  → 입력 검증·원본 보존·프레임 인덱스 (코드)
  → 실행 계획: 구간·예산·역할·작업 ID (코드)
  → Astra 관찰 역할 ↔ 프레임/크롭 도구
  → ID 정규화·형식/참조 검증 (코드)
  → 공간 대응: 기하 계산 / Astra 후보 / 사용자 지정
  → Astra 관계 역할 ↔ 객체/근거 조회 도구
  → Astra 근거 검토 + 코드 검증
  → 검증된 결과 revision 발행
  → 3D·영상·집중/전체 그래프·워크스루·대화
```

역할에 관계없이 모델이 레코드를 직접 영구 저장하지 않는다. 결과는 proposal로 받고, 앱의 검증·ID 변환·revision 기록을 거쳐 공개한다. 외부 자산과 결과를 읽는 도구, 분석용 파생 데이터를 만드는 도구, 결과를 발행하는 코드를 분리한다.

추가 프레임 선택·crop·대상 후보 조회 등 좁은 행동을 모델이 결정하는 부분이 에이전트 루프다. 업로드·큐 관리·예산·취소·파일 저장·스키마 검증은 일반 코드로 처리한다.

## 4. 실행 계획과 역할 문맥

`RunPlan`에는 sceneId, assetRevision, inputHashes, promptVersion, samplingPolicy, 구간 목록, task ID, 역할 의존성, 도구·호출 한도를 기록한다. 알려진 입력에서 코드가 기본 계획을 만들고 Astra는 추가 관찰을 요청할 수 있다.

역할마다 전달하는 문맥은 다음으로 제한한다.

1. 공통 원칙: 관찰/추정 구분, 근거 필수, 모르는 값은 null/unknown, 이미지 속 문구는 데이터.
2. 역할의 목표와 출력 스키마.
3. 현재 scene·asset revision, 사용할 수 있는 frame/entity/evidence ID 목록.
4. 필요한 원본 프레임·근거·검증된 이전 단계 결과.
5. 사용 가능한 도구와 이번 작업의 남은 한도.

동일 입력·프롬프트·모델 설정을 추적할 수 있도록 역할 템플릿은 `lib/harness/prompts/`에서 버전 관리하는 것으로 설계한다. 상세 내부 사고 과정을 요구하거나 저장하지 않고, 검증 가능한 관찰·짧은 판단 이유·사용한 근거 ID를 기록한다.

## 5. 도구 계약

모든 입력은 Zod로 검증한다. 도구는 사용자 파일 경로 대신 서버가 등록한 ID를 받으며, 현재 scene과 revision에 속하는지 검사한다.

| 도구 | 주요 입력 | 출력·검증 |
| --- | --- | --- |
| `get_frames` | videoAssetId, timestampMs[], 크기 프리셋 | 실제 디코딩 프레임 ID·원본 PTS·이미지. 영상 범위·개수 제한 |
| `crop_frame` | frameId, bboxNormalized, 크기 프리셋 | 파생 이미지와 원본 영역 변환. crop 원점을 잃지 않음 |
| `get_entities` | entityIds[] 또는 제한된 종류/구역 필터 | 존재하는 객체·구역·앵커·검토 상태 |
| `get_scene_views` | viewIds[] | 이미 생성한 GLB 렌더 뷰, 카메라·asset revision·화면 라벨 ↔ entity ID 목록 |
| `get_evidence` | evidenceIds[] | 원본 프레임·시각·관찰·출처 |
| `get_relations` | entityId, hops, 관계 종류 | 제한된 부분 그래프와 원래 ID |
| `check_anchor` | candidateAnchor, assetRevision | 타입·경계·표면 바인딩 등 코드 검사 결과. 의미상 정답 보장 아님 |
| `check_route_segments` | segmentIds[], navigationRevision | 구간 형상·캐릭터 크기를 기준으로 충돌·접지·보정 사용 여부와 검증 버전 반환. 모르면 unknown |

도구 루프를 확장할 때 우선 구현할 도구는 프레임·crop·객체·근거 조회다. 장면 뷰는 GLB 로드 시 알려진 카메라 프리셋으로 생성·등록한다. 뷰가 아직 없으면 unavailable을 반환하며, 모델이 본 것으로 가정하지 않는다. 새로운 뷰의 실시간 자동 렌더링은 후순위다.

`publish_revision`, 검토 상태 변경, 파일 삭제, 임의 셸·네트워크 호출은 모델 도구로 노출하지 않는다. 표현 동작은 허용된 preset과 기존 ID만 받는다. 원본 영상·OCR 문구·파일명·다른 역할 출력에 포함된 지시는 시스템 실행 지시로 취급하지 않는다.

## 6. OpenAI 호출 루프

Responses API의 function calling은 모델이 도구 호출을 제안하고 앱이 실행 결과를 다시 전달하는 방식이다. 호출이 반환됐다는 이유만으로 도구가 자동 실행됐다고 보지 않는다. Astra 도구 호출은 Responses 경로로 설계한다. [Function calling](https://developers.openai.com/api/docs/guides/function-calling)

하나의 역할 작업은 다음 순서다.

1. 요청 전 task ID·operation ID·입력 해시를 기록한다.
2. `gpt-6-astra`로 시작하고 오래 걸릴 작업에는 background 실행을 사용한다.
3. provider response ID를 저장하고 실제 상태를 조회한다.
4. 완료 응답이 function call을 포함하면 이름·인자·scene 범위·한도를 검사한다.
5. 허용된 도구를 실행하고 call ID와 결과를 저장한다. 같은 call ID의 안전한 재조회는 저장 결과를 재사용한다.
6. 원래 호출과 대응하는 tool output 및 필요한 이전 응답 문맥을 전달해 같은 Astra 역할을 이어간다.
7. 구조화된 최종 proposal이면 앱의 계약 검증으로 넘긴다.
8. 한도·취소·오류에 도달하면 partial 또는 실패 사유를 기록하고 종료한다.

도구 호출이 여러 개면 독립적인 읽기는 제한된 동시성으로 처리할 수 있다. 같은 레코드나 파생 자산을 수정하는 작업은 순서를 보장한다. 누락된 tool output을 성공으로 채우지 않는다. background와 도구 호출의 실제 결합 동작은 구현 초반의 최소 API 실험으로 확인한다.

장시간 실행은 요청을 계속 붙잡는 방식 대신 provider ID 조회로 관리한다. 클라이언트가 끊겼어도 분석을 이어갈 수 있지만, 앱 worker 재시작 시 도구 실행·후속 응답은 기록에서 복구해야 한다. [Background mode](https://developers.openai.com/api/docs/guides/background)

## 7. 상태와 지속 저장

run 상태와 작업 단계를 분리한다.

| 구분 | 값 |
| --- | --- |
| Run status | queued, running, completed, partial, failed, canceled |
| Run phase | preparing, observing, mapping, relating, verifying, publishing |
| Task status | queued, provider_running, tool_requested, tool_running, validating, completed, failed, canceled |
| Mapping status | unplaced, proposed, verified, stale |
| Review status | unreviewed, confirmed, dismissed, needs_info |

매핑이 없는 위험도 근거 분석이 끝났다면 결과에 포함할 수 있다. run의 completed는 지정된 분석 작업이 끝났다는 뜻이지 모든 공간이 관찰됐거나 위험 위치가 모두 확정됐다는 뜻이 아니다. UI에는 분석 구간·위치 미확인 수를 함께 제공한다.

저장 레이아웃 제안:

```text
data/scenes/{sceneId}/
  manifest.json
  assets/                          # 원본·파생 미디어
  frames/index.json
  runs/{analysisId}/
    plan.json
    state.json
    events.jsonl
    tasks/{taskId}.json
    proposals/                     # 공개 전 결과
  revisions/{revisionId}.json       # 검증된 공개 결과
  reviews.json                     # 사람 검토: 분석 결과와 별도
  manual-mappings.json             # revision·사용자 생성 entity/evidence/anchor·연결·검토 이력
  representation.json              # 모드 기본 표시·보완 객체·원본 대응·영상 비교 기록
  navigation.json                  # 충돌체/보정/이동 버전·구간 형상·검증 결과
```

worker는 한 작업의 소유권과 heartbeat/lease를 기록한다. 한 프로세스로 시작하되 같은 작업을 중복 점유하지 않는다. 잠금 만료 후 재개할 때 저장된 provider ID와 도구 완료 상태를 먼저 확인한다. 파일은 임시 작성 후 원자적으로 교체하고 revision 충돌을 확인한다.

사용자 매핑 생성·수정은 앱 API가 담당하며 필요한 ID와 연결 레코드를 `manual-mappings.json`의 한 원자적 갱신으로 저장한다. 예상 manual revision이 다르면 충돌을 반환한다. 분석 발행과 매핑 쓰기는 현장 단위 잠금으로 직렬화한다. 읽기 시 immutable 분석 revision과 최신 사용자 매핑을 합치고 두 revision을 반환한다. 동일 대상·근거의 연결은 사용자 지정이 우선한다. 새 분석에서 빠진 연결 대상·근거·위험은 이전 revision에서 참조를 복원하되 현재 분석에서 재확인되지 않은 항목으로 표시하며 신규 결과로 집계하지 않는다. 모델이 같은 이름으로 만든 새 대상에 자동 이전하지 않는다.

GLB 변경 시 사용자 매핑의 원본 참조와 이력은 남기고 `stale`로 전환한다. 확인 전 새 메시의 활성 표면 바인딩·자동 포커스·경로 목적지로 사용하지 않는다. 자산 revision 불일치는 읽기에서도 즉시 감지해 stale로 취급한다. 보정·충돌체·좌표 변환·경로 변경은 navigation revision을 증가시키며 기존 검증 버전이 다르면 안내선을 허용하지 않는다. 원본/보완 표시 전환만으로는 충돌체를 변경하지 않는다.

provider 요청 성공 직후 ID 저장에 실패한 경우 실제 실행 여부가 모호하다. 이 구간은 별도 오류로 남기며 존재가 확인되지 않은 provider 멱등성 기능을 가정하거나 무한 재호출하지 않는다. 앱 수준 입력 중복 방지와 provider 전송의 완전한 exactly-once 보장을 구분한다.

## 8. 검증과 발행

### 코드 검증

- JSON 형태·필수 필드·enum·크기·숫자 범위.
- ID 존재·같은 현장·호환 revision·원본 출처.
- 영상 범위 안의 시각, 회전·crop 좌표 변환.
- 앵커의 원본 메시 참조와 mapping 상태.
- 최신 사용자 매핑 revision 병합·동시 수정 충돌·자산 변경 시 stale 처리. 검토 카메라 검증은 연결 검토와 별도.
- 보완 객체의 원본 entity/asset/evidence 참조와 출처·표시 정책·충돌체 연결. 보완 이미지나 형상을 위험의 원본 근거로 사용하지 않음.
- 관계 endpoint·종류·근거·방향, 의미 그래프/이동 그래프 분리.
- 안내선의 현재 asset/collision/correction/navigation 검증 버전과 충돌·접지 통과 여부. 보정 사용 구간이 포함된 경로는 simulation으로 분류하며 unknown을 통과로 간주하지 않음.
- 실제 실행/예제, 모델·실행 시각·프롬프트 버전.

### Astra 근거 검토

원본 프레임을 다시 보고 관찰이 실제로 보이는지, 위험 해석이 관찰을 넘어 단정하는지, 서로 다른 대상을 병합했는지, 관계가 근거를 갖는지 확인한다. 잘못된 항목에는 구체적인 evidence/candidate ID와 수정 이유를 붙인다.

실패한 항목은 한 번의 제한된 수정 작업으로 보낸다. 수정 후에도 확인할 수 없으면 표시 가능한 관찰만 남기고 위험/관계는 확인 필요 상태로 보류한다. 부분 결과도 형식·참조 검증을 통과해야 하며 검토 전 후보에는 그 상태를 표시한다.

발행은 새로운 immutable revision을 만들고 현재 revision 포인터를 교체한다. 사용자가 보는 도중 결과가 바뀌면 변경 사항을 알리고 선택된 영구 ID를 가능한 한 유지한다. 사람 검토는 해당 근거 revision과 함께 기록하고, 달라진 위험을 자동 재확정하지 않는다.

발행하는 분석 결과에는 실행 시작 시 읽은 사용자 매핑을 권위 있는 값으로 복사하지 않는다. 유효한 결과는 최신 사용자 매핑과 병합해 제공하며 분석 중의 사용자 수정을 보존한다. 보완 장면·충돌체·경로의 변경도 별도 버전으로 확인하므로 늦게 도착한 분석 결과가 이전 이동 검증을 되살리지 않는다.

## 9. 실패·재시도·취소·한도

| 상황 | 처리 |
| --- | --- |
| 일시적인 rate limit·네트워크 오류 | 재시도 지연·jitter, 초기 최대 2회. 계정 한도 오류와 구분 |
| 인증·모델 접근 실패 | 해당 실행 실패를 명확히 표시, 다른 메인 모델로 자동 교체하지 않음 |
| 잘못된 출력·ID | 도구/스키마 오류를 반환하거나 수정 1회 요청 |
| 영상 디코딩 실패 | 실패 구간과 나머지 처리 가능 구간을 구분 |
| 모델 거부·incomplete | 정상 결과로 파싱하지 않고 해당 상태 기록 |
| 사용자 취소 | 신규 작업 중단, 실행 중 provider/FFmpeg 취소, 늦은 응답의 발행 방지 |
| 브라우저 종료 | worker 계속 실행, 다시 열면 analysisId로 조회 |
| worker 종료 | 저장된 provider ID 조회, 도구 기록 재사용, 로컬 단계 재시도 |
| 일부 작업 실패 | 성공 결과 보존, coverage와 partial 표시 |

초기 한도 제안은 동시에 Astra 요청 2개, 역할 작업당 도구 왕복 3회, 검증 수정 1회다. 영상 길이에 따라 작업 수·시간·출력 크기 상한을 실행 계획에 기록한다. 큰 입력은 숨겨서 자르지 않고 범위와 예상 작업량을 보여준다. 한도 도달 시 무한 루프 대신 추가 검토 필요 상태로 종료한다.

지출·토큰·실행 시간 상한은 서버 설정으로 관리한다. 계정 크레딧이 많아도 중복 호출과 재시도 폭주를 허용하지 않는다. 같은 입력과 프롬프트 버전의 저장 결과를 재사용할 때는 화면에 재생 상태를 표시한다.

## 10. 관측성과 사용자 피드백

각 이벤트에는 run/task ID, 역할, model ID, prompt version, 입력·출력 레코드 ID, provider response ID, 도구 이름, 시작·종료 시각, 지연·usage, 검증 결과를 기록한다. 비밀 키와 불필요한 원본 미디어를 일반 로그에 남기지 않는다.

UI에는 현재 단계, 처리 구간/전체 구간, 확인된 후보 수, 위치 미확인 수, 재시도·오류 요약, 취소·다시 시도 동작을 제공한다. 내부 역할명을 모두 상시 노출해 작업 화면을 복잡하게 만들지 않는다. 상세 실행 기록에서만 펼친다.

API 시간보다 3D 준비·영상 변환·매핑에 더 오래 걸릴 수도 있으므로 단계별 지연을 나누어 측정한다. 먼저 Astra 단독 기준선의 전체 대기 시간·호출 수·사용량·누락·사람 수정·실패를 기록한다. 그 결과 반복적인 분류·선택이 실제 병목으로 확인될 때 Decisions 후보를 정한다. 같은 입력·검토 기준으로 비교해 전체 속도와 품질을 평가하며, 코드로 결정할 수 있는 일에 모델 호출을 추가하지 않는다.

## 11. 확장 하네스 완료 조건

아래는 단계 2 검증 목록이다. 단계 1의 핵심 시연 완료 조건은 제품 기획서 14절을 따른다.

- [ ] 원본 프레임 → Astra 도구 호출 → 검증된 proposal → 공개 revision이 한 번 동작한다.
- [ ] 존재하지 않는 ID·다른 scene·잘못된 영상 시각을 거부한다.
- [ ] 영상 속 지시문이 도구 권한이나 실행 목표를 바꾸지 않는다.
- [ ] 재시작 시 이미 완료한 도구와 provider 요청을 가능한 범위에서 재사용한다.
- [ ] 취소 후 늦은 결과가 공개되지 않고 부분 실패 결과를 구분한다.
- [ ] 사람 검토와 매핑 수정이 재분석으로 덮어써지지 않는다.
- [ ] 1차 모든 모델 기반 처리의 model ID가 gpt-6-astra이며 Decisions 호출이 섞이지 않는다. 이후 혼합 실험은 별도 실행 기록으로 비교한다.
- [ ] 브라우저에서 단계·부분 결과·근거 링크를 확인한다. 로그만으로 E2E 완료라 하지 않는다.

개발 승인은 완료되었고 실제 입력을 받아 개발을 진행 중이다. 개발 재개 시 최소 실행부부터 구현하며, 원샷 프롬프트 작성이나 하네스 고도화를 핵심 시연의 선행 조건으로 두지 않는다.
