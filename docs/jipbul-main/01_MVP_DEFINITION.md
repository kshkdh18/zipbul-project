# 짚불 제품·기술 전체 기획안

버전: 1.1 · 작성일: 2026-10-09 · 상태: **개발 승인 완료, 사용자 요청으로 영상 전달까지 개발 대기**

초기 기획 PDF, AGENTS.md, 사용자의 최신 요구사항을 통합한 메인 앱 설계다. 이전 v0.1의 사진 묶음 입력, 워크스루 후순위, 모델 미정 제안을 대체한다. 사용자는 수정 요구사항과 함께 개발 착수를 승인했고 이후 영상 전달까지 대기를 요청했다. **Astra 기반 핵심 시연을 먼저 완성한 뒤 평가 결과로 Decisions 수요를 판단한다. 제품 구현 완료를 뜻하지 않는다.**

함께 읽을 문서: [에이전트 하네스 설계](./02_AGENT_HARNESS.md), [ID·근거·그래프 연결 JSON 예시](./examples/scene-review.example.json).

## 1. 제품 정의와 확정 요구사항

**짚불은 현장의 GLB와 원본 영상을 받아, Astra가 찾은 위험과 영상 근거를 3D 공간·관계 그래프에 연결하고, 전문적인 분석 화면과 게임형 워크스루로 현장을 이해하고 점검하는 웹앱이다.**

대표 데모 사용자는 현장 안전관리자다. 재난구조대의 원격 공간 이해는 확장 사용 사례로 유지한다. 제품의 가치는 위험 후보를 나열하는 데서 끝나지 않고 **어디에 있고, 무엇을 보고 판단했으며, 주변과 어떤 관계이고, 무엇을 확인해야 하는지**를 한 흐름으로 보여주는 것이다.

| 항목 | 사용자 확정 내용 |
| --- | --- |
| 시간 | 앞서 정한 대회 시작 시점부터 총 6시간. 기획 수정으로 시간을 다시 시작하지 않는다. |
| 입력 | **3D 메시 GLB + 원본 영상**을 입력받는다. |
| 담당 | 스캐너·컨트롤러는 팀원이 개발 중. 이 작업은 `zipbul/` 메인 앱에 집중한다. |
| 탐사 | **분석 모드와 워크스루 모두 필수**. 이동과 게임형 상호작용을 제공한다. |
| 표현 | 위험·근거가 매핑된 곳을 클릭하면 줌인·카메라 접근·대상 강조가 일어난다. |
| 연결 | 객체·위험·근거·공간·경로를 ID로 매핑한다. |
| 그래프 | JSON 기반으로 시작한다. 위험 관계와 경로를 이해하기 쉽게 표현하며 **전체 펼치기도 제공**한다. |
| AI | 개발과 1차 제품의 모델 기반 처리는 **GPT-6 Astra (`gpt-6-astra`)**로 진행한다. Decisions는 핵심 흐름 완성 후 평가에서 필요가 확인된 영역에만 검토한다. |
| UI | 무채색 배경, 강조색 1~2개, 일관된 버튼·타입·간격. 영상·3D가 화면의 중심이다. |
| 표현 보완 | 게임 장면의 가구 형상·재질·조명·그림자·접지감은 필수다. 실제 영상과 비교하고, 시간이 부족하면 대상 수를 줄여 대표 구역의 완성도를 지킨다. |
| 예산 | 약 $7,800 크레딧 보유는 사용자 제공 정보다. 실제 잔액·계정 권한은 조회하지 않았다. |
| 절차 | 기획 승인·개발 지시 완료. 사용자 요청으로 영상 전달까지 개발 대기 중이다. |
| 대회 조건 | 개발은 Codex만, AI 모델·서비스는 OpenAI만 사용한다. 단일 Git 모노레포 유지. |

아직 실제 GLB·영상, 추가 메타데이터, Astra 계정 접근, 제출 방식은 확인하지 않았다. 현재 로컬 제품 코드도 없다. 아래 기술 구성·성능 수치·시간 배분은 구현 기준과 목표이며 검증 결과는 아니다.

환경 확인: 루트 `.env`에 값이 있는 `OPENAI_API_KEY`가 등록되어 있고 Git에서 제외되며 추적되지 않는 것을 확인했다. 키 값은 출력하지 않았다. 실제 API 호출·Astra 접근 권한·잔액은 아직 검증하지 않았다. 구현 시 `zipbul/` 서버와 worker가 루트 환경 파일을 명시적으로 읽거나 부모 프로세스에서 환경변수를 주입받도록 구성한다. 브라우저 공개 환경변수로 전달하지 않는다.

## 2. 핵심 사용자 경험

### 2.1 분석 모드

1. GLB와 영상을 열면 AI 분석 완료 전에도 공간과 영상을 탐색할 수 있다.
2. 검증을 통과한 위험 후보가 순차적으로 추가된다. 분석된 영상 구간과 미처리 구간을 구분한다.
3. 위험 목록·3D 마커·그래프·영상 영역에서 하나를 선택하면 같은 ID가 모든 화면에 반영된다.
4. 카메라가 해당 검토 지점으로 접근하고 원본 영상의 근거 시각이 열린다. 관찰 내용, 위험 해석, 위치 연결 상태, 점검 우선순위를 확인한다.
5. 담당자가 확인·보류·오탐을 기록하고, 관련 관계를 펼치거나 Astra에 질문한다.

### 2.2 워크스루

- `W/A/S/D` 이동, 마우스 시점, `Shift` 빠른 이동, `Esc` 포인터 잠금 해제·일시정지, `E` 대상 확인을 제공한다.
- 벽·바닥 충돌, 중력·접지, 유효한 시작 위치, 추락·끼임 시 복귀를 구현한다. 프레임 속도와 무관하게 이동 거리를 계산한다.
- HUD는 조준점, 현재 점검 대상, 근거 검토 진행, 다음 대상 방향을 중심으로 최소화한다.
- 대상을 바라보고 선택하면 이동 입력을 멈추고 검토 시점으로 전환한다. 영상 근거 패널을 닫으면 원래 위치로 돌아간다.
- 단순히 가까이 갔다고 점검 완료로 처리하지 않는다. 근거 확인과 사용자 검토 기록이 있어야 진행 수에 반영한다.
- **근거 따라 걷기**: 위험을 체크포인트로 선택하고 방문·검토 상태를 표시한다. 이동 연결이 확인된 구간에만 바닥 안내선을 그린다.

게임 요소는 이동의 손맛, 대상 발견, 상호작용, 체크포인트와 진행 피드백이다. 위험 개수를 많이 찾는 경쟁 점수·전투·과장된 보상은 넣지 않는다. 점프와 정교한 계단 자동 오르기는 후순위다. 두 모드 사이에 대상 선택은 유지하되 카메라·이동 입력은 동시에 활성화하지 않는다.

## 3. 클릭 포커스와 3D 표현

| 단계 | 화면 동작 | 기준 |
| --- | --- | --- |
| 선택 | 공통 상태에 hazard/entity/evidence ID 반영 | 각 패널이 별도의 위험 목록을 만들지 않음 |
| 접근 | 약 0.6~1.0초 동안 저장된 검토 카메라로 이동 | 단순 FOV 확대에만 의존하지 않고 대상 크기·가림을 고려 |
| 강조 | 얇은 윤곽, 표면 강조, 작은 ID 라벨 | 선택되지 않은 공간은 약하게 낮추되 구조는 유지 |
| 근거 | 영상 시각 이동, 해당 프레임과 영역 강조 | 추적하지 않은 박스를 영상 전체에 계속 표시하지 않음 |
| 관계 | 관련 연결과 영향 경로 강조 | 관계 이름·방향·추정 여부 표시 |
| 복귀 | 이전 시점과 워크스루 위치 복원 | Esc·사용자 조작으로 전환 취소 가능 |

카메라가 벽을 뚫고 날아가는 장면을 피한다. 유효한 이동 경로가 없으면 짧은 화면 전환으로 **검토 시점**에 이동하고 실제 걸어간 기록과 구분한다. 모션 감소 설정에서는 즉시 전환한다.

위 표의 카메라 접근·공간 강조는 필요한 매핑이 존재하는 항목에 적용한다. 아래 예외도 필수 동작이다.

| 데이터 상태 | 클릭 동작 |
| --- | --- |
| 위치·대상 영역·검토 카메라 있음 | 검증된 접근·윤곽·표면 강조와 영상 근거 표시 |
| 위치만 있고 객체 영역이 분리되지 않음 | 유효한 검토 시점과 점 마커만 사용. 윤곽·표면 영역을 지어내지 않음 |
| 위치 미확인 | 영상 근거와 설명을 열고 수동 연결 제공. 카메라 접근·공간 강조·경로 이동은 실행하지 않음 |
| 매핑 또는 검토 카메라가 오래되었거나 검증되지 않음 | 재검토 안내와 영상 근거 우선. 자동 접근 보류 |

선택 효과는 단면 보기, 한 번의 짧은 스캔 표면 드러내기, 근거 방향의 얇은 연결선이다. 상시 네온·블룸·점멸·장식 입자는 사용하지 않는다.

Astra는 `focus_entity`, `highlight_region`, `show_evidence`, `reveal_relation_path`, `suggest_inspection_order` 같은 **표현 지시 JSON**을 만들 수 있다. 앱이 대상 ID·효과 종류·카메라 범위를 검증한 뒤 실행한다. API 응답의 JavaScript·셰이더를 런타임에 그대로 실행하지 않는다. 개발 중 GPT로 재질·셰이더·연출 코드를 만드는 것과 운영 중 임의 코드를 실행하는 것은 구분한다.

렌더링과 이동은 로컬 코드가 담당한다. 카메라를 움직일 때마다 API를 호출하지 않는다.

## 4. UI 디자인 시스템

### 4.1 시각 기준

| 요소 | 기본값 제안 |
| --- | --- |
| 배경 | `#111315`, 패널 `#1B1E21`, 경계 `#303438` |
| 텍스트 | 본문 `#F2F3F4`, 보조 `#B4BAC1`. 실제 렌더링에서 대비 확인 |
| 강조색 1 | `#E5A84B`: 위험·주의·선택된 위험 영역 |
| 강조색 2 | `#7BA8D8`: 근거·현재 탐색 경로·중립적인 선택 |
| 상태 | 색 외에 문구·아이콘·실선/점선 사용 |
| 글자 | 시스템 한글 산세리프, 본문 14px, 패널 제목 16px, 화면 제목 20px, 시각·ID는 고정폭 숫자 |
| 간격 | 4·8·12·16·24·32px |
| 조작부 | 기본 높이 36px, 모서리 4~6px, 일관된 버튼·탭·입력 |
| 배제 | 불필요한 그라데이션·네온·유리 효과·큰 둥근 카드 반복·이모지·과한 그림자 |

원본 영상·GLB 텍스처의 실제 색은 유지한다. 강조색 제한은 UI 표시 체계에 적용한다. 오류·우선순위는 색만으로 전달하지 않는다.

### 4.2 화면 배치

**분석:** 상단 48px에 현장·모드·분석 상태, 왼쪽 약 220px에 위험 목록, 중앙 작업 영역에 3D와 영상/근거를 약 65:35로 둔다. 분할선을 조절하고 어느 쪽도 크게 볼 수 있다. 그래프·대화는 필요할 때 여는 하단 또는 별도 작업 패널이다. 좁은 창에서는 보조 패널을 접어 미디어 영역을 지킨다.

**워크스루:** 3D가 화면 대부분을 차지한다. 상단 한 줄의 모드·현장명·종료, 모서리의 목표·진행, 하단의 짧은 조작 안내만 유지한다. 근거 패널은 선택 시에만 연다. 영상·대화 입력 중에는 이동 키를 처리하지 않는다.

**전체 그래프:** 작업 영역 또는 전체 화면을 사용한다. 전체 맞춤·확대·검색·필터·구역별 접기/펼치기·전체 펼치기·선택 대상으로 이동을 제공한다. 돌아오면 분석/워크스루의 카메라와 선택을 복원한다.

처리 중에는 “영상 구간 3/8 처리”, “관계 검토 중”처럼 실제 작업 상태를 표시한다. 근거 없는 진행률·ETA를 만들지 않는다. ID·모델·실행 정보는 펼칠 수 있는 상세 정보에 둔다.

## 5. 입력·원본·파생 데이터

기본 입력은 GLB와 원본 영상 두 파일이다. 파일명은 강제하지 않고 asset ID로 관리한다. 카메라 자세·내부 파라미터·깊이·시간 동기화 정보는 있으면 받지만 필수 입력으로 올리지 않는다.

| 작업 | 결과 |
| --- | --- |
| 접수 | 파일 종류·읽기 가능 여부 확인, ID·해시 생성, 원본 보관 |
| GLB 검사 | 경계·노드·삼각형·텍스처·좌표·스케일 정보 |
| 영상 검사 | 코덱·길이·해상도·회전·시간축 |
| 재생 준비 | 필요 시 브라우저용 MP4 프록시, 원본 시각 변환 정보 |
| 분석 준비 | 원본 PTS 기준 프레임 인덱스, 이미지 회전·크롭 변환 |
| 탐사 준비 | 렌더링용 GLB와 별도의 충돌용 파생 데이터 |

GLB는 glTF의 미터·우수 좌표계·Y-up 관례를 기준으로 처리하되 스캐너의 실제 방향·스케일을 확인한다. 중심·크기 조정은 `worldFromAsset`에 기록하고 모든 앵커에 동일하게 적용한다. 단위 확인 전에는 정확한 미터 거리처럼 표시하지 않는다. [glTF 명세](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)

**GLB와 영상만으로 영상의 모든 픽셀을 정확한 3D 좌표에 연결할 수 있다고 가정하지 않는다.** 같은 공간·촬영 세션인지 확인하고, 연결 정보가 없으면 대응 검토를 제공한다. 프록시나 추정 장면을 원본 근거로 대체하지 않는다.

## 6. 공간 재구성과 근거 매핑

### 6.1 공간 표현의 세 층

| 층 | 역할 | 표시 |
| --- | --- | --- |
| 수집 공간 | 원본 GLB·원본 텍스처 | 실제 수집 결과 |
| 탐사용 보정 | 단순화 충돌체·바닥 구멍 보정·이동 경계 | 탐사 시뮬레이션용 보정 |
| 추정 보완 | 개략 형상·재질·객체 후보 | 별도 토글, “추정 보완” 표시 |

우선 GLB의 방향·크기·재질·조명을 개선한다. 작은 구멍 때문에 이동이 막히면 원본을 보존한 채 탐사용 충돌체를 보완한다. 미관측 구역은 미관측으로 남긴다.

**대표 구역의 게임 장면 보완은 필수 범위다.** 주요 가구를 알아볼 수 있는 형상, 실제 영상에 가까운 재질, 일관된 조명·그림자·접지감을 구현하고 원본 영상과 비교한다. 시간이 부족하면 보완 대상 수를 줄인다. 대표 구역 전체를 거친 메시나 기본 도형만으로 남긴 채 완료로 보지 않는다. 추정 형상의 출처 표시는 유지한다.

각 이동 구간에는 `sourceSupport: supported / partial / unknown`, `usesExplorationCorrection`, `correctionIds`를 기록한다. 원본 지지는 이동을 뒷받침하는 수집 형상의 유무이며 현장 안전 등급이 아니다. 바닥 보정은 원본 지지 상태를 바꾸지 않는다. 보정을 하나라도 사용하는 경로는 `pathClassification: simulation`과 “시뮬레이션 경로”로 표시한다. 알려지지 않은 연결은 미검증으로 유지한다. 실제 통행 가능성이나 안전한 경로로 표현하지 않는다.

추가 재구성은 영상의 여러 시점·알려진 치수·랜드마크를 근거로 Astra가 보완 대상을 제안하고 제한된 기본 형상·재질로 표현한다. 보완한 벽·문을 실측처럼 표시하거나 보완 모델을 위험의 원본 증거로 사용하지 않는다. 6시간 안에 완전 자동 사진측량을 새로 만드는 것보다 원본 충실도·이동 가능성·매핑·표현에 집중한다.

### 6.2 매핑 방식

**수동 영상 영역–GLB 표면 연결은 처음부터 정식 기능으로 구현한다.** 같은 촬영 세션인지, 자세·내부 파라미터·시간 동기화 정보를 추가 받을 수 있는지 확인한다. 정보가 없어도 수동 연결을 기본으로 개발하며 자동 매핑 가능 여부를 기다리지 않는다. 현재 영상 전달을 기다리는 것은 사용자의 별도 대기 요청에 따른 것이다.

| 상황 | 처리 | 사용자 표시 |
| --- | --- | --- |
| 자세·내부 파라미터·공간 정합 정보 있음 | 시간 동기화된 광선과 메시/깊이의 교차로 후보 위치 계산 | 자동 추정 위치 · 검토 필요 |
| 영상과 공간 대응을 사람이 확인 가능 | 영상 영역과 GLB 표면을 차례로 선택 | 사용자 지정 위치 |
| Astra가 객체·구역 후보를 대응 | 번호가 붙은 장면 뷰·알려진 객체 중 후보 선택 | AI 연결 제안 · 미확정 |
| 대응 근거 부족 | 영상·그래프에만 유지, 좌표는 null | 공간 위치 미확인 |

자동 투영에는 회전·크롭·왜곡·카메라 축·촬영 시간차가 반영되어야 한다. 카메라 위치를 위험 위치로 대용하지 않는다. 자동 계산 성공과 사람의 검토 완료는 다른 상태다. 위치가 없으면 영상 근거로 이동하고 3D 이동 버튼은 비활성화한다.

### 6.3 단일 메시와 영구 ID

GLB 메시 하나가 방 전체여도 앱은 독립적인 `entityId`를 부여한다. 대상 영역은 삼각형 집합·표면 패치·개략 경계로 정의할 수 있다. GLB 노드 이름이나 Three.js 런타임 UUID를 영구 식별자로 사용하지 않는다.

앵커는 asset revision, 노드 경로, primitive/triangle index, barycentric 좌표 또는 표면 패치, 원본 좌표 위치를 기록한다. 단순화·재출력으로 토폴로지가 바뀌면 바인딩을 다시 검증한다. 객체 ID가 유지된다는 이유로 이전 삼각형 번호를 새 메시에서 재사용하지 않는다.

## 7. ID 중심 데이터 모델

| 레코드 | 핵심 연결 |
| --- | --- |
| Scene | 현장·좌표계·자산·현재 결과 revision |
| Asset | GLB·원본 영상·프록시·프레임·원본 관계 |
| Frame | videoAssetId·원본 PTS·timestampMs·이미지 변환 |
| Entity | 구역·문·케이블·상자·통로 같은 지속적인 대상 |
| Evidence | frameId·영상 시각/구간·정규화 영역·관찰 내용 |
| Anchor | 위치·표면 바인딩·mappingMethod·mappingStatus·검토 카메라 |
| Hazard | entityIds·evidenceIds·anchorIds·위험 해석·점검 우선순위·이유 |
| Relation | source/target ID·종류·방향·근거 ID·사실/추정/수동 구분 |
| Route | 점검 순서·체크포인트·이동 그래프 참조·검증 상태 |
| Review | hazardId·확인/보류/오탐·검토자·시각 |
| AnalysisRun | 입력 해시·모델·프롬프트 버전·provider ID·실행/사용량 기록 |

영구 ID는 앱이 만든다. 모델은 전달받은 ID를 참조하거나 임시 candidateId를 제안하며 서버가 검증 후 정식 ID로 변환한다. `H-01` 같은 화면 표시 번호는 별도 displayId다.

여러 프레임에 보이는 같은 대상은 하나의 entity에 여러 evidence를 연결한다. 이름이 비슷하다는 이유만으로 병합하지 않는다. 재분석은 새 analysisId·revision으로 기록하며 사람 검토는 별도로 보존한다. 근거가 바뀌면 재검토 필요 표시를 한다.

공통 선택 상태는 sceneId·entityId·hazardId·evidenceId·routeId·mode·cameraBookmark로 구성한다. 모든 패널은 같은 정규화 데이터에서 읽는다.

필수 검증: 참조 ID 존재, 동일 현장과 호환 revision, 영상 길이 안의 시각, 이미지 기준 0~1 영역, 미확인 좌표 null, 관계 의미·근거·추정 표기, 실제 실행/재생/예제 구분. 형식 예시는 [연결 JSON](./examples/scene-review.example.json)에 둔다.

## 8. 관계 그래프: 집중 보기와 전체 펼치기

### 8.1 보기 모드

| 보기 | 목적·동작 |
| --- | --- |
| 집중 | 선택 위험의 1홉 관계로 시작, 클릭해 2홉 이상 확장 |
| 관계 경로 | 대상/관찰 → 위험 해석 → 영향 구역·경로 → 점검 행동을 따라 보기 |
| 전체 | **전체 노드·관계를 펼칠 수 있음**. 기본 그룹이 있어도 전체 펼치기로 모두 접근 |
| 구역별 | 구역 또는 대상별 묶기/접기, 중요한 교차 관계 유지 |

기본 전체 보기에는 전체 펼치기·전체 맞춤·노드 선택을 둔다. 핵심 시연 이후 검색, 관계 종류·검토 상태 필터, 미니맵, 자동 묶기를 확장한다. 필터 적용 시 표시 수/전체 수를 알려 누락된 것으로 오해하지 않게 한다. 모든 레코드에 접근 가능해야 한다.

레이아웃은 안정적인 방향 배치를 사용한다. 노드마다 ID·짧은 제목·종류를 표시하고 선에는 관계 이름·화살표를 둔다. 사실은 실선, 추정은 점선, 선택한 경로만 강조한다. 관련 없는 선까지 상시 움직이지 않는다. 전체 보기에서 돌아와도 이전 선택과 카메라를 복원한다.

### 8.2 관계 의미

`located_in`은 대상의 구역, `observed_in`은 관찰 근거, `concerns`는 위험의 대상, `supports`는 판단의 근거, `may_affect`는 경로·구역에 대한 잠재 영향, `may_compound`는 다른 위험과의 복합 가능성이다. 뒤의 두 관계는 근거·설명·추정 표기가 필수다. 정보가 없으면 관계를 만들지 않는다.

**관계 그래프와 이동 그래프는 구분한다.** 의미 관계의 화살표가 실제 걸을 수 있는 연결을 뜻하지 않는다. 이동 그래프는 실제 위치·검증된 연결 구간을 따로 가지고 ID로 연결된다.

### 8.3 창의적인 표현

**근거 따라 걷기:** 관계 경로를 점검 체크포인트로 바꾼다. 공간에서 대상 확인 → 영상 근거 열기 → 다음 관계 검토의 순서를 연결한다. 근거 검토가 끝난 노드의 상태를 함께 갱신한다.

이동선은 충돌·바닥 연결을 확인한 구간에만 그린다. 미확인 구간은 연결 미확인으로 남긴다. 출입구처럼 보이는 객체를 자동으로 비상구로 확정하지 않는다. 이동 가능성은 현장 통행 안전 보장이 아니다.

시간이 남으면 “이 장애물을 정리했다고 가정하면?” 비교를 제공한다. 가정 시나리오에서 관련 관계만 비교하며 실제 검토 기록을 변경하거나 검증되지 않은 위험 감소율을 생성하지 않는다.

## 9. Astra 분석과 영상 처리

Astra는 공식 문서상 이미지 입력을 지원하고 영상·오디오 직접 입력은 지원하지 않는다. 원본 영상을 프레임으로 추출해 시각과 ID를 함께 전달한다. GLB는 구조 요약·번호가 붙은 렌더 뷰·알려진 앵커로 전달하며 모델이 원본 GLB를 직접 해석한다고 가정하지 않는다. [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)

처리 순서: **원본 검사 → 프록시/프레임 → Astra 관찰·위험 후보 → 추가 프레임·crop 확인 → 공간 대응 → 관계 통합 → 근거 검증 → 결과 revision 공개**. 각 단계는 [하네스](./02_AGENT_HARNESS.md)가 실행·저장·복구한다.

처음에는 약 2초 간격 기본 샘플과 장면 변화 보강, 요청당 8~12프레임, 동시 Astra 요청 2개를 제안한다. 실제 영상 길이·세부 대상 크기·응답 시간에 따라 조절한다. 후보 주변 시각은 더 촘촘히 추출하고 고해상도 crop을 재검토한다. 기본 샘플에서 안 보였다고 안전하다고 결론내리지 않는다.

프레임의 원본 PTS와 시간 단위를 저장하고 프록시·회전·크롭 변환을 추적한다. 가변 FPS 영상을 프레임 번호/FPS만으로 시간 매핑하지 않는다. 시간축에 처리 구간과 미처리 구간을 표시한다. [FFprobe 문서](https://www.ffmpeg.org/ffprobe-all.html)

위험 분석·관계 해석은 Astra high, 대화·표현 지시는 Astra medium을 초기 설정으로 제안한다. 형식은 Zod/JSON Schema로 검증하고, 사실·ID·근거·좌표는 별도로 검증한다. 대화는 현재 결과 revision과 불확실한 항목을 받아 근거 ID를 반환한다. 위치 불확실성과 위험 해석의 불확실성을 하나의 정밀 점수로 합치지 않는다. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

## 10. 장시간 실행과 Decisions 활용

### 10.1 Astra 장시간 실행

기본은 Responses API `background: true`와 provider 응답 ID 저장·조회다. 브라우저 연결과 분석 실행을 분리하며 모델 추론 자체의 가속 기능으로 설명하지 않는다. 실제 상태를 조회하고 완료·실패·취소를 처리한다. [Background mode](https://developers.openai.com/api/docs/guides/background)

로컬 worker가 작업 기록을 소유하고 브라우저는 우선 2초 간격 폴링으로 진행을 읽는다. 긴 작업을 웹 요청에서 fire-and-forget으로 실행하지 않는다. 재시작 시 provider ID로 상태를 복구하며 로컬 영상 변환은 별도 재시도한다. 검증된 부분 결과부터 볼 수 있다.

### 10.2 Decisions는 Astra 기준선 평가 이후 검토

공식 문서상 Decisions는 공개 베타이고 현재 **gpt-6-luna만 지원**한다. 조건 판단·선택지 분류·등급 점수에 사용한다. Astra를 Decisions 엔드포인트에 넣는 설계는 하지 않는다. [Decisions 가이드](https://developers.openai.com/api/docs/guides/decisions)

**1차 구현에는 Decisions 호출·라우터·사전 분류를 넣지 않는다.** Astra 기반으로 핵심 시연 흐름을 완성하고, 단계별 지연·호출 수·사용량·실패/재시도·사람 수정·근거 누락을 기록해 기준선을 만든다. ID 조회·좌표 변환·충돌·클릭 예외처럼 코드로 결정할 수 있는 작업은 처음부터 코드로 처리한다.

이후 실제 사용에서 반복적이고 병목이 되는 판단을 찾는다. 대표 근거 선택, 가구/재질 후보 분류, 중복 후보 정리, 매핑 후보 순위, 자연어 조작 분류는 평가 후보이며 현재 채택 기능은 아니다. 같은 입력과 검토 기준으로 Astra 단독과 혼합 구성을 비교하고, 전체 사용자 대기 시간이 줄면서 근거 누락·오분류·수동 수정이 악화되지 않는 영역에만 적용한다. 작은 평가셋이면 표본 규모와 한계도 기록한다. Decisions 결과만으로 위험 부재·실제 통행 안전을 확정하지 않는다.

도입 필요가 확인되면 그 시점의 SDK·입력 형식·계정 접근을 검증한다. 미지원 시 Astra 흐름을 유지한다. [Decisions API 참조](https://developers.openai.com/api/reference/typescript/resources/decisions/methods/create)

### 10.3 크레딧 운용

보유 크레딧은 Astra의 추가 시점·crop·교차 검증·표현 설계에 활용한다. 핵심 모델을 비용 때문에 자동 대체하지 않는다. 입력 해시·프롬프트 버전 기반 중복 방지, 실행별 사용량·지연 기록, 서버 설정의 지출·동시 요청 한도를 둔다. 크레딧 전체 소진을 목표로 삼지 않는다. 이번 기획 과정에서는 유료 API 호출을 실행하지 않는다.

Drei의 모드별 카메라 제어와 Rapier의 충돌체 연동을 사용하고, React Flow 렌더링과 그래프 배치 계산은 분리한다. [Drei Controls](https://drei.docs.pmnd.rs/controls/introduction), [CameraControls](https://drei.docs.pmnd.rs/controls/camera-controls), [React Three Rapier](https://github.com/pmndrs/react-three-rapier), [React Flow 레이아웃](https://reactflow.dev/learn/layouting/layouting)

패키지 버전은 구현 시작 때 Next/React/R3F/Rapier 호환성을 확인하고 lockfile에 고정한다. 현재 머신의 Node·FFmpeg 실행 파일 존재만 확인했으며 앱·API 호환성을 검증한 것은 아니다. 별도 Python 도구가 필요하면 uv를 사용한다.

기본 실행 대상은 시연용 Mac의 장기 실행 Node 서버·worker·데스크톱 브라우저다. 공개 URL이 필요하면 장기 실행 서버와 영구 파일 저장 방식을 정한다. 로컬 JSON을 서버리스 영구 저장소로 취급하지 않는다. 인증·조직 관리·대규모 다중 사용자 서비스는 초기 범위에 넣지 않는다.

## 12. 성능·복구 목표

아래는 실제 시연 장비에서 확인할 목표이며 보장이 아니다.

- 워크스루 60fps 지향. 30fps 미만이 지속되면 픽셀 비율·그림자·효과를 줄인다.
- 선택 피드백은 약 100ms 이내, 카메라 접근은 약 1초 이내를 목표로 한다.
- 영상 플레이어·3D Canvas를 모드 간 공유하고 GLB를 중복 로드하지 않는다.
- 원본 렌더링 메시와 충돌용 단순화 메시를 분리한다. 방 전체를 단일 convex hull로 만들어 통로를 막지 않는다.
- 바닥 구멍 보정과 실제 벽 충돌을 구분하고 검토된 복귀 지점을 둔다.
- 필요 없는 텍스처·지오메트리·Object URL을 해제하며 프레임 전체를 GPU에 올리지 않는다.
- 분석 단계·부분 결과를 먼저 제공하고 전체 완료 시간은 실측한다.
- JSON 기록은 원자적 교체·작업 잠금·revision 검사로 보호한다. 분석 결과와 사람 검토를 분리해 서로 덮어쓰지 않는다.

## 13. 6시간 구현 순서와 범위 조정

우선순위는 **두 모드, 실제 이동·충돌, 대표 구역의 게임 장면, 점검 선택·영상 근거 연결·수동 매핑, 기본 전체/집중 그래프**다. Astra 분석과 최소 실행·저장·검증을 여기에 연결한다. 그래프 검색·필터·자동 묶기, 다단계 에이전트 루프 등 하네스 고도화는 핵심 시연을 통과한 뒤 확장한다. 워크스루를 회전 뷰로 대체하거나 전체 그래프를 빼고 완료라고 하지 않는다.

| 순서 | 결과 | 완료 기준 |
| --- | --- | --- |
| 1 | 실제 입력·Astra 최소 호출·계약 | GLB·영상 재생과 이미지 분석 성공 |
| 2 | 2모드·공통 ID·선택 | 같은 예시 ID로 공간·영상·그래프 연결 |
| 3 | 이동·충돌·대표 구역 게임 장면·수동 연결·근거 시각 | 실제 영상 비교와 공간 이동·대상 검토·복귀 |
| 4 | 프레임 처리·하네스·Astra | 원본 영상에서 근거 있는 결과와 진행 상태 |
| 5 | 매핑 검토·전체/집중 그래프·대화 | 같은 위험의 공간·근거·관계·응답 일치 |
| 6 | 표현·예외·시연 | 실제 입력으로 반복 가능한 흐름 |

초기 예산 제안은 연동·기반 20분 / 2모드·입력 70분 / 이동·포커스 70분 / Astra·하네스·관계 85분 / 통합·표현 70분 / 최종 검증·발표 45분이다. 기획에 이미 사용한 시간은 차감한다. 개발 재개 시 실제 남은 시간에 맞춰 대표 구역 게임 장면과 핵심 시연을 우선 배분하며 마감은 늘리지 않는다.

1차 범위에서 Decisions는 제외한다. 시간이 부족하면 컨트롤러 내장 연동, 그래프 편의 기능, 하네스 고도화, 자동 대응, 가정 비교, 추가 구역·장식 효과를 줄인다. 대표 구역 게임 장면 보완은 유지하되 대상 수를 줄인다. 이동선 자동 생성이 지연되면 검토된 체크포인트와 관계 경로를 제공하고 미확인·보정 연결을 구분한다. 수동 매핑은 자동 매핑으로 표시하지 않는다.

스캐너 팀원에게는 작은 GLB+영상 샘플과 좌표·촬영 동기화 정보 유무만 우선 확인한다. API 접근 실패 시 메인 모델을 임의 대체하지 않는다. 마지막 45분은 기능 추가를 멈추고 실제 브라우저 검증·시연 보관에 사용한다.

## 14. 완료 정의와 검증

- [ ] 실제 GLB·영상 입력부터 재생·분석·검토까지 완료한다.
- [ ] 분석 모드의 탐색과 워크스루 이동·충돌·접지·Esc·복귀가 실제 장비에서 동작한다.
- [ ] 대표 구역의 가구 형상·재질·조명·그림자·접지감을 구현하고 실제 영상과 비교한다.
- [ ] 매핑된 항목의 포커스·근거 연결과 미매핑/영역 미분리 항목의 클릭 예외가 동작한다.
- [ ] 수동 매핑이 정식 기능으로 동작하고, 바닥 보정 구간·시뮬레이션 경로의 출처 표시가 유지된다.
- [ ] 위치 추정·사람 지정·위치 미확인, 위험 해석·사람 검토를 각각 구분한다.
- [ ] 원점/스케일 변환 후 앵커가 유지되고 영상 회전·프록시·가변 FPS에서도 시각이 맞는다.
- [ ] 기본 집중·전체 펼치기가 동작하고 전체 레코드에 접근할 수 있다. 묶기·검색·필터는 이후 확장한다.
- [ ] 그래프·3D·영상·대화의 선택이 동일 ID를 가리키고 의미 관계/이동 경로를 구분한다.
- [ ] 실제 Astra 결과가 원본 근거를 가진다. 예제·저장 재생·실시간 실행을 구분한다.
- [ ] 최소 실행부의 근거/ID 검증·실패 표시·취소·결과 저장·검토 보존을 확인한다. 다단계 도구 루프와 복구 고도화는 핵심 흐름 이후 검증한다.
- [ ] 영상 패널 입력 시 캐릭터가 움직이지 않고 선택 전환·성능 목표를 검증한다.

데모 제안: **실제 파일 열기 → 위험 클릭·카메라 접근·영상 근거 → 전체 그래프에서 집중 관계 경로 → 워크스루·근거 체크포인트 → Astra 질문·근거 링크 → 미확인 항목 표기**. 로컬 실행, 외부 배포, 실제 데이터 검증을 각각 기록한다.

## 15. 현재 진행 상태

사용자가 최신 수정사항과 함께 개발 착수를 승인했다. 이후 영상 전달까지 대기를 요청해 현재 개발은 일시 대기 중이다. 실제 파일·API 접근·추가 메타데이터·제출 URL 필요 여부는 확인할 외부 조건이며, 자동 매핑 메타데이터 부재는 수동 연결을 통한 개발의 차단 조건이 아니다.

개발 재개 시 이 문서의 핵심 흐름과 Astra 기준선을 먼저 구현한다. 별도 원샷 프롬프트 작성이나 재승인을 구현의 선행 조건으로 두지 않는다. 핵심 시연이 통과한 뒤 그래프 편의 기능·하네스 고도화·평가 기반 Decisions 최적화를 진행한다.
